# Resumable E2E lifecycle

## Goal

`test:e2e` runs every Playwright E2E suite sequentially against `https://preview.codeline.work` (the requested production origin); `test:e2e:dev` explicitly selects the managed development environment. Runs resume automatically from a validated, target-bound checkpoint and safely remove owned data on success or after 24 hours. Cleanup is attempted after every invocation, including failures. Verify a full fresh suite and deliberate failure/resume.

## Existing constraints and decisions

- There are 19 spec files/28 tests; Playwright already uses one worker. Tests currently issue/purge synthetic identities through guarded local SQLite scripts; production fixture APIs do not yet exist. Do not loosen the local fixture guard or launch an unmanaged service.
- Preview is the public origin of the repository-managed combined server; its built service currently serves this checkout. Use the managed service for verification and preserve one-worker tests.
- Production fixture lifecycle must use authenticated, narrowly scoped application APIs, not direct test-runner database writes. Reuse existing identity/purge logic server-side and existing dependencies (Valibot). Never delete records lacking verified E2E ownership.
- Checkpoint storage is `/tmp/opencode/codeline/e2e/`, versioned and Valibot-validated, with target, origin, identity, created time, completed suites, and resource IDs. A stale (>24h) run is purged before beginning a fresh run; target mismatch never resumes.
- Successful run data is removed and its checkpoint cleared; failed run data/checkpoint remain available until expiry. Cleanup of other expired runs executes in `finally`, reports errors, and verifies absence across every integration the suites actually create. No Stripe/mail/storage resources are presently created by these suites; don't introduce unrelated integrations.

### Task 2, increment 1 (identity fixtures only)

- The combined server registers `POST /api/_e2e/fixtures/runs` (`{ "runId": "[0-9a-z]{6,40}" }`), `GET /api/_e2e/fixtures/runs/:runId`, `POST /api/_e2e/fixtures/runs/:runId/expire`, and `DELETE /api/_e2e/fixtures/runs/:runId`. Issue returns two members' opaque tokens **once**; status never returns tokens; expiry invalidates their sessions and prunes their compact journal events; deletion returns `exists: false` and is idempotent. All responses are no-store. A 409 on existing or unverifiable ownership requires operator investigation rather than retrying with an unsafe prefix purge.
- The gate is a dedicated `Authorization: Bearer <E2E_FIXTURE_API_TOKEN>` secret (at least 32 characters, configured **only on the managed server**, transmitted by the future runner over HTTPS). No cookie, origin header, or general application role grants this API. No routes are registered without that secret and a configured canonical OIDC issuer (`OIDC_ISSUER`, or Authworks provider issuer) and `OIDC_ORGANIZATION_ID`. Do not commit this credential. The server database must have migration 0018 applied before enabling the gate. Do not enable on an untrusted public deployment without restricting who can obtain the secret.
- `e2e_fixture_run` persists exact run ID, server creation timestamp, issuer, organization and the two issued user IDs. Issue is atomic and rejects preexisting identities/users. Status, expiry and purge check both users' E2E display names/emails, exact indexed subjects, issuer, organization mapping and exclusive identity/membership rows before acting. Purge deletes only those verified user IDs, relying on database FK cascades for their dependent application records. The legacy local prefix purge was not modified and is **not** used by this API.
- **Not complete resource cleanup:** this increment does not register or verify test-specific project/seed state, diagnostics stored in systemd, any external integration, or resources belonging to non-fixture users. It does not implement 24-hour run rollover/scheduling/checkpoints, migration of the E2E specs/helper, or verification of all application resource cascades and external resources. Later increments must inventory/record each run-owned resource and verify its absence across integrations; keep shared seed untouched. No production-run E2E test has been attempted yet.

### Task 2, diagnostics increment

- Migration 0022 creates `e2e_fixture_diagnostic`, scoped by a verified run marker and member ID. Only authenticated, verified fixture members' sanitized `/api/diagnostics/logs` entries are diverted from stdout into this table; unverified ownership fails closed. Ordinary users continue to write to the existing journal. Storage is capped at 128 entries per run, 64 KiB per entry; oldest entries are evicted transactionally.
- `GET /api/_e2e/fixtures/runs/:runId/diagnostics` uses the existing dedicated bearer gate, verifies fixture identity and every stored member, returns bounded entries without tokens and with no-store; missing runs return `{ "exists": false, "entries": [] }`. Purge refuses foreign diagnostic owners, deletes owned rows and checks absence before removing the run marker. `managedOriginDiagnosticsIngestion.spec.ts` now polls this API instead of systemd, preserving event/redaction checks.
