# Codeline setup and feature-parity plan

## Goal

Create `@adaptive-ds/codeline` as a Bun/SolidJS/Hono application that reimplements `pi-web` with the requested exclusions, reaches feature parity before novel features, and uses Zero for persistent synchronized state.

## Approach

- Start with architecture and dependency compatibility discovery across the referenced local projects and upstream documentation.
- Bootstrap repository conventions from sibling Adaptive projects while assigning Codeline-specific metadata, workspace names, docs, and operations.
- Establish a minimal TanStack AI-native vertical slice with separate UI/API routes, streaming boundaries, validation, tests, and local Podman services.
- Add `pi-web` parity incrementally, committing after each completed phase.
- Implement requested extensions only after parity: multiple servers/agents, subagents, reloadable Git-backed configuration, durable streaming retries, and SSO/OIDC last.

## Durable decisions

- Package name: `@adaptive-ds/codeline`.
- Runtime and package manager: Bun.
- UI: SolidJS using `@adaptive-ds/solid-ui`.
- Validation: Valibot, subject to compatibility confirmation at integration boundaries.
- Backend: Hono unless Zero imposes a conflicting server requirement.
- UI and API routes remain separate and expose explicit streaming/error test seams.
- Live model output streams directly to the client; PostgreSQL stores durable application state and Zero synchronizes finalized state.
- Secrets belong in ignored `.env`; distributable configuration uses `.env.example` without secret values.
- Exclusions from `pi-web`: Pi ecosystem/plugins, MCP, full-text web search, and custom right scrollbar.
- Search is metadata substring matching, with Zero-backed synchronization/preloading where applicable.
- Provider OAuth is excluded; initial provider targets are local CLIProxyAPI and Codex-LB configurations.
- Hono is suitable for the Bun API layer; Zero runs as a separate synchronization service rather than replacing the application API.
- TanStack AI supports SolidJS and custom streaming transports; Valibot remains appropriate for application boundary validation.
- Use a TanStack AI-native execution core; Pi JSONL compatibility is not required.
- Persist an accepted user prompt before generation. Stream transient sequenced events directly to the client, then persist finalized assistant and tool entries to PostgreSQL; do not treat Zero as the token-stream transport.
- Durable reconnect must survive connection drops and application-process restarts using event IDs and PostgreSQL-backed replay. Detect stale streams using a configurable inactivity timeout.
- `git-store` tracks validated reloadable configuration, not conversation transcripts.
- Configuration/provider credentials use secret indirection and never enter committed configuration or Git history.
- Local Zero development uses an explicit development identity; SSO/OIDC remains last.
- Local Postgres for Zero/dev services uses the `postgres:18-alpine` image (latest stable Alpine major; Postgres 19 is beta-only and not used yet).
- Drizzle ORM is the database access and migration layer.
- Zero uses the latest API from the pinned `/home/david/opensource/zero` checkout, not registry `@rocicorp/zero@1.8.0`; `packages/zero` is registered with Bun and linked into Codeline after cloning. Bun link is intentionally local-only and non-reproducible from a clean clone/CI for now; generated package/tarball support is deferred.
- Codeline development uses default rootless Podman storage, `/home/david/.local/share/containers/storage` and `/run/user/1001/containers` on the development host; ops scripts must not create project-specific `/tmp` or `/run/user/.../codeline-podman-*` roots.
- Validated configuration changes are automatically committed to a local Git repository without automatic remote pushes.
- Initialize Git and publish `david1gp/codeline` as a private GitHub repository; commit and push after each completed phase.
- Source is organized by bounded context, not by technical layer. Domain contexts are `identity`, `servers`, `agents`, `session`, `message`, and `stream`.
- Each domain context owns its layers: `schema/` for Valibot contracts, `api/` for Hono route registration, `actions/` for application operations, and `db/` for Drizzle tables and repositories.
- `src/database/` holds only shared persistence infrastructure: the client, transactions, ready-check, migrations, `databaseSchema.ts` composition, `zeroSchema.ts`, and helpers that cannot belong to one context.
- `src/api/` holds platform HTTP only: health, readiness, errors, testing, request parsing, and route composition. Domain routes live in `<context>/api/`.
- `src/server/` is the HTTP process entrypoint. The server domain context is `src/servers/` so the two names stay distinct.
- Finalized-message persistence accepts plain-text `user` and `assistant` records only in the pre-execution slice; tool/system records remain part of later execution work.
- Finalized-message sequence numbers are allocated by the server transaction, writes are idempotent per session and client request ID, conflicting reuse is rejected, archived sessions are read-only, and successful appends update session activity ordering.
- Zero navigation uses the Solid `ZeroProvider` and synchronized reads only; Hono remains the command path. The browser reads `VITE_ZERO_CACHE_URL` with a local `http://127.0.0.1:6003` fallback and uses the shared explicit development identity `local-development`.
- Session selection is URL-backed with the `session` query parameter. The initial navigation shows existing active sessions only, clears selection when a session becomes unavailable, renders finalized user/assistant messages read-only, and retains API health separately from Zero connection status.
- Zero Cache serves named-query transformations through the Bun/Hono `POST /api/query` endpoint. The browser identity key is `local-development`, while the durable development user row ID remains `development:local-development`.
- Managed Zero Cache startup resets only its disposable local replica volume so stale replica metadata cannot prevent restart; PostgreSQL durable data and browser cache remain intact.
- The first chat-execution slice uses a deterministic in-process TanStack AI adapter and `POST /api/sessions/:sessionId/chat`; `threadId` must equal the session ID, the final plain-text user prompt is persisted before streaming, and a finalized assistant message is persisted only after successful completion. Provider integration and durable replay are separate later increments.
- Development agents must use Codeline's repository-managed systemd user services under `ops/dev/`; they must not start substitute or unrelated services, and must diagnose and repair a managed service instead of bypassing it.
- Local development PostgreSQL data and Podman containers may be reset when useful for repair. Example data must be seeded deterministically through a repository-owned script with checked-in fixtures, following `~/opensource/zero/apps/zbugs`; zbugs is also the reference for working Zero sync configuration.
- Managed development ports use a dedicated conflict-free range: UI `6000`, API `6001`, PostgreSQL `6002`, and Zero Cache `6003`.
