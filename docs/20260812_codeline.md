# Codeline setup and feature-parity plan

## Goal

Create `@adaptive-ds/codeline` as a Bun/SolidJS/Hono application that reimplements `pi-web` with the requested exclusions, reaches feature parity before novel features, and uses Zero for persistent synchronized state.

## Approach

- Start with architecture and dependency compatibility discovery across the referenced local projects and upstream documentation.
- Bootstrap repository conventions from sibling Adaptive projects while assigning Codeline-specific metadata, workspace names, docs, and operations.
- Establish a minimal TanStack AI-native vertical slice with separate UI/API routes, streaming boundaries, validation, tests, and local Podman services.
- Add `pi-web` parity incrementally, committing after each completed phase.
- After verification closes each phase, delegate `/commit` to a dedicated subagent that loads the commit skill, reviews and groups only that phase's changes, creates conventional commit(s), and pushes before implementation begins on the next phase.
- Build an isolated `/demo` UI showcase from deterministic dummy data so visual iteration can proceed without backend integration or changes to active backend/domain paths.
- Implement requested extensions only after parity: multiple servers/agents, subagents, reloadable Git-backed configuration, durable streaming retries, and SSO/OIDC last.
- Use Tailwind CSS v4 utilities for application styling, retaining only the Tailwind entrypoint, theme/base rules, and narrowly necessary global accessibility CSS.

## Durable decisions

- Package name: `@adaptive-ds/codeline`.
- Runtime and package manager: Bun.
- UI: SolidJS using `@adaptive-ds/solid-ui`.
- Validation: Valibot, subject to compatibility confirmation at integration boundaries.
- Backend: Hono unless Zero imposes a conflicting server requirement.
- UI and API routes remain separate and expose explicit streaming/error test seams.
- Live model output streams directly to the client; PostgreSQL stores durable application state and Zero synchronizes finalized state.
- Secrets belong in ignored `.env`; distributable configuration uses `.env.example` without secret values.
- Exclusions from `pi-web` (anti-features, not later work): Pi ecosystem/plugins, MCP, full-text web search, custom right scrollbar, trusted folders / project trust, editing or limiting AI capabilities, and AI permission management. Codeline does not persist per-project trust decisions, prompt users to trust a workspace, or gate skills/extensions/settings behind a trust dialog the way `ProjectTrustStore` / `ProjectTrustDialog` do in pi-web. It also does not expose tool presets such as `off` / `read-only` / `default` / `full`, capability pickers, skill dormancy as a permission control, or per-tool / per-command approval, allowlists, or restricted-mode UI. Path-root validation for filesystem and Git access is a separate technical safety check, not user trust or permission management.
- Search is metadata substring matching, with Zero-backed synchronization/preloading where applicable.
- Provider OAuth is excluded; initial provider targets are local CLIProxyAPI and Codex-LB configurations.
- Hono is suitable for the Bun API layer; Zero runs as a separate synchronization service rather than replacing the application API.
- TanStack AI supports SolidJS and custom streaming transports; Valibot remains appropriate for application boundary validation.
- Use a TanStack AI-native execution core; Pi JSONL compatibility is not required.
- Persist an accepted user prompt before generation. Stream transient sequenced events directly to the client, then persist finalized assistant and tool entries to PostgreSQL; do not treat Zero as the token-stream transport.
- Durable reconnect must survive connection drops and application-process restarts using event IDs and PostgreSQL-backed replay. Detect stale streams using a configurable inactivity timeout.
- `git-store` tracks validated reloadable configuration, not conversation transcripts.
- Configuration/provider credentials use secret indirection and never enter committed configuration or Git history.
- Local Zero development uses an explicit development identity; SSO/OIDC remains last.
- Local Postgres for Zero/dev services uses the `postgres:18-alpine` image (latest stable Alpine major; Postgres 19 is beta-only and not used yet).
- Drizzle ORM is the database access and migration layer.
- Zero uses the latest API from the pinned `/home/david/opensource/zero` checkout, not registry `@rocicorp/zero@1.8.0`; `packages/zero` is registered with Bun and linked into Codeline after cloning. Bun link is intentionally local-only and non-reproducible from a clean clone/CI for now; generated package/tarball support is deferred.
- Codeline development uses default rootless Podman storage, `/home/david/.local/share/containers/storage` and `/run/user/1001/containers` on the development host; ops scripts must not create project-specific `/tmp` or `/run/user/.../codeline-podman-*` roots.
- Validated configuration changes are automatically committed to a local Git repository without automatic remote pushes.
- Initialize Git and publish `david1gp/codeline` as a private GitHub repository; commit and push after each completed phase.
- Source is organized by bounded context, not by technical layer. Domain contexts are `identity`, `servers`, `agents`, `session`, `message`, and `stream`.
- Each domain context owns its layers: `schema/` for Valibot contracts, `api/` for Hono route registration, `actions/` for application operations, and `db/` for Drizzle tables and repositories.
- `src/database/` holds only shared persistence infrastructure: the client, transactions, ready-check, migrations, `databaseSchema.ts` composition, `zeroSchema.ts`, and helpers that cannot belong to one context.
- `src/api/` holds platform HTTP only: health, readiness, errors, testing, request parsing, and route composition. Domain routes live in `<context>/api/`.
- `src/server/` is the HTTP process entrypoint. The server domain context is `src/servers/` so the two names stay distinct.
- Finalized-message persistence accepts plain-text `user` and `assistant` records only in the pre-execution slice; tool/system records remain part of later execution work.
- Finalized-message sequence numbers are allocated by the server transaction, writes are idempotent per session and client request ID, conflicting reuse is rejected, archived sessions are read-only, and successful appends update session activity ordering.
- Zero navigation uses the Solid `ZeroProvider` and synchronized reads only; Hono remains the command path. The browser reads `VITE_ZERO_CACHE_URL` with a local `http://127.0.0.1:6003` fallback and uses the shared explicit development identity `local-development`.
- Session selection is URL-backed with the `session` query parameter. The initial navigation shows existing active sessions only, clears selection when a session becomes unavailable, renders finalized user/assistant messages read-only, and retains API health separately from Zero connection status.
- Zero Cache serves named-query transformations through the Bun/Hono `POST /api/query` endpoint. The browser identity key is `local-development`, while the durable development user row ID remains `development:local-development`.
- Managed Zero Cache startup resets only its disposable local replica volume so stale replica metadata cannot prevent restart; PostgreSQL durable data and browser cache remain intact.
- The Solid composer uses `useChat` from `@tanstack/ai-solid` with the `fetchServerSentEvents` connection adapter pointed at `POST /api/sessions/:sessionId/chat` and `threadId` set to the session ID. It renders only for an authorized selected active session, and the hook is keyed on the session ID so navigation discards the in-flight turn rather than leaking it.
- Zero finalized messages stay authoritative. `transientMessagesResolve` reconciles the in-flight turn against durable rows by role and trimmed content, consuming one durable occurrence per transient entry so repeated identical prompts do not disappear early, and dropping empty in-flight placeholders.
- Composer behavior: Enter submits, Shift+Enter inserts a newline, the send action is disabled while empty or busy, chat client errors render in an alert, and `stop()` aborts the in-flight run. Aborted runs persist no assistant message.
- The first chat-execution slice uses a deterministic in-process TanStack AI adapter and `POST /api/sessions/:sessionId/chat`; `threadId` must equal the session ID, the final plain-text user prompt is persisted before streaming, and a finalized assistant message is persisted only after successful completion. Provider integration and durable replay are separate later increments.
- Chat resolves the selected session's primary-agent provider configuration at execution time. Stored provider configuration is validated before runtime creation, provider environment/runtime creation is dependency-injected, and the deterministic provider remains the development fixture default.
- Chat stream IDs derive deterministically from session and run IDs. A run checkpoints sequence zero, persists each event before SSE delivery, and terminalizes with a durable finish or error event; completed repeated requests replay durable events without re-execution, while interrupted runs finalize no assistant message.
- Chat replay eligibility depends on a checkpoint having persisted events, not merely existing, so status inspection cannot suppress first execution. Zero Cache reaches the managed API through `host.containers.internal:6001` for query and mutation transforms.
- Development agents must use Codeline's repository-managed systemd user services under `ops/dev/`; they must not start substitute or unrelated services, and must diagnose and repair a managed service instead of bypassing it.
- Local development PostgreSQL data and Podman containers may be reset when useful for repair. Example data must be seeded deterministically through a repository-owned script with checked-in fixtures, following `~/opensource/zero/apps/zbugs`; zbugs is also the reference for working Zero sync configuration.
- Managed development ports use a dedicated conflict-free range: UI `6000`, API `6001`, PostgreSQL `6002`, and Zero Cache `6003`.
- Metadata search is URL-backed and restricted to case-insensitive substring matching of session/server/agent metadata; message content is excluded and SQL wildcard characters are treated literally.
- Project filesystem access is read-only and rooted in an injected canonical directory used for path-safety validation. This is not a user-managed trusted-folder feature. Public paths are strict relative POSIX paths; all symlinks and traversal forms are rejected, reads/downloads are bounded and no-follow, and host paths never appear in public results or errors.
- Provider configuration is a strict discriminated contract for deterministic, CLIProxyAPI, and Codex-LB targets. Credentials are environment references resolved through provider-specific allowlists; literal secrets, arbitrary environment access, and credential-bearing URLs are rejected.
- Git parity does not include worktree integration or isolation. The Git surface shows the current branch and other local branches and allows switching, renaming, and deleting branches within the configured canonical project repository.
- The `/demo` showcase is client-only, uses deterministic local fixtures, does not call or require backend services, and stays isolated from concurrent backend/domain implementation paths.
- Demo pathname routing uses `/demo` for its index and `/demo/<scenario>` for deterministic visual states. Typed fixtures and scenario modules live under `src/ui/demo/` and must not import API, Zero, database, filesystem, provider, or domain modules.
- Demo surfaces must pass an axe-core WCAG 2 A/AA audit with zero violations: muted foregrounds are at least `#5f6879` on light backgrounds and `#9da8b8` on dark ones, status accents use `#1f7047`/`#8b6417`, each scenario exposes exactly one `h1` (the conversation title), and scrollable `pre` blocks are keyboard focusable.
- The demo adopts pi-web's representative responsive three-region shell: session navigation, chat workspace, and optional file panel. It covers welcome, populated/streaming/error chat, nested session branches, file tree/view/preview/diff, configuration overlays, stats/system-prompt surfaces, extensions/status, minimap/history, and mobile layouts. It does not include trusted-folder, capability-limit, or AI-permission surfaces.
- Solid Router is mounted once at the UI root. Explicit client routes cover the application and demo surfaces, while the existing `session` query parameter remains the session-selection contract rather than becoming path state.
- Production history fallback serves the UI shell only for known application/demo paths; `/api/*` and unknown server paths retain normal non-HTML handling.
- Session branches persist an immutable nullable `parentSessionId` set only by the branch command; generic creation rejects parent input. Parent deletion retains descendants by clearing their parent link, and Zero exposes both the parent field and self-referential relationships for the synchronized client tree.
- Finalized and in-flight chat entries share the same sanitized Markdown body renderer. Partial streaming Markdown may reflow as delimiters complete, but transient reconciliation and durable Zero authority remain unchanged.
- Project text previews remain read-only. Markdown files expose per-tab Source/Preview state using the existing sanitized renderer, default to Source on first open, and preserve display mode while switching open tabs.
- Mobile workspace session navigation uses the existing synchronized list in an accessible overlay drawer, closes on selection/backdrop/Escape, restores trigger focus, and leaves the desktop sidebar unchanged.
- Task 6 is parallelized around stable shared contracts: multi-server/agent selection and Git-backed configuration can proceed concurrently; durable run/attempt foundations form a third backend lane; bounded subagents consume the resulting target, snapshot, retry, cancellation, and budget contracts; SSO/OIDC remains serialized last.
- Phase transitions are commit-gated: a dedicated subagent must load and execute the commit skill after phase verification, including formatting, semantic staging, conventional commit creation, and push, before the next phase starts.
