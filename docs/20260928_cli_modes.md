# Codeline CLI: local, server, and interactive modes

## Goal

Provide `codeline` with one-shot and persistent interactive terminal conversation. Both interfaces select a backend: local in-process execution (default, no listener), an already-running local Codeline server, or a remote Codeline server. The terminal UI loads Pi coding-agent theme JSON and uses Pi-style terminal components without copying Pi's agent runtime.

## Decisions

- Bun is the CLI runtime. Use `@stricli/core` for command parsing; share the existing Valibot request/response schemas with server operations after parsing, avoiding duplicate payload definitions.
- CLI settings live in `${XDG_CONFIG_HOME:-$HOME/.config}/codeline/config.json`; CLI flags override config. Keep server-owned configuration separate. Do not silently use the development preview as the remote default.
- The default backend is local in-process. An explicit server backend points to an existing local or remote server. Do not start an ad-hoc server: the repository-managed systemd preview owns development services and SQLite.
- Local execution reuses the same session/chat/run orchestration as the API through the composed Hono application's in-process `fetch`, without binding a port. No second agent implementation or large chat-route extraction is needed. A code-injected local identity policy preserves persisted membership and project-root scoping; network server startup rejects that policy. Preserve reconciliation, cancellation, and resource cleanup.
- Remote interim authentication accepts the current opaque identity-session token via `Cookie`, with appropriate origin on unsafe requests; it is not a JWT. Proper browser login/API tokens are out of scope. Never print credentials.
- Interactive rendering uses Pi's published TUI package if compatible with Bun. Accept Pi coding-agent theme JSON format, including variables/color resolution; support selecting a theme in the Codeline XDG config and reading Pi's normal theme files (and explicitly configured theme files). Keep terminal theme separate from the web UI theme.
- One-shot mode streams the reply without requiring a TTY; interactive mode keeps session continuity and allows interruption/cancellation. Both share backend/session operations and option semantics.

## Task 2 increment: remote one-shot

With `CODELINE_SESSION_TOKEN` temporarily supplied in the process environment, and `PROJECT_ID` or `SESSION_ID` set to the relevant remote identifier, run:

```sh
bun src/cli/main.ts run "Explain the project" --backend https://your-codeline-server.example --project "$PROJECT_ID"
bun src/cli/main.ts run "Continue the explanation" --backend https://your-codeline-server.example --session "$SESSION_ID"
```

The token is the existing opaque identity-session cookie value, not a JWT. There is no token flag, login flow, or token persistence. Do not put it in CLI config or command arguments; clear it from the environment after use. Unsafe requests send the server origin; authenticated requests reject redirects. `--project` is a remote project ID, never a local path; it applies to new sessions. An existing `--session` cannot be combined with a project option (including a configured project).

New sessions discover the first server and its first root primary agent through the existing typed API, matching the browser's unsaved default selection. The server owns project resolution, authorization, and execution defaults; absent targets or rejected requests fail rather than invent IDs.

Stdout receives only appended assistant text, without a progress banner or added newline. This is snapshot polling (100 ms between successful reads), **not raw token SSE**: `/api/events` contains lifecycle summaries only. Retryable snapshot errors back off to 1.6 seconds, with at most six consecutive retries. A run succeeds only after successful terminal status and final answer recovery. Finalization clears active `partialText`, so the existing HTTP run-detail endpoint recovers fast-run output and the final suffix. Its transcript is bounded/redacted; a truncation marker or non-append-only replacement causes a nonzero failure rather than silently printing an incomplete answer as success.

Failures go to stderr with nonzero exit. Ctrl-C aborts polling and requests server cancellation with a separate, bounded request, removes the signal handler, and exits 130. During chat admission it waits for the bounded admission request to settle before cancelling the client-generated run ID, avoiding an untracked detached run. Cancellation failures are reported, not represented as successful cancellation.
